SHEET 01 / SYSTEM OVERVIEW

1. System Overview

Citizens report civic problems — potholes, water pollution, and similar issues. Each report is routed through an AI worker for classification, then connected to a university (which proposes a solution) and an industry partner (which funds it).

Actors

RoleCapabilities
CitizenSubmit problems, view own submissions
AdminVerify / assign problems, view platform-wide stats
UniversitySubmit proposals for assigned problems
IndustryFund approved proposals
AI WorkerSystem actor — classifies problems via the internal API

SHEET 06 / CORE DATA FLOW

6. Core Data Flow

  1. Citizen submits POST /problems → Postgres insert (status=submitted)
  2. Backend pushes a job onto the Redis queue: { problemId, text }
  3. Backend responds in under 200ms — it does not wait for classification
  4. Worker picks the job up from Redis
  5. Worker runs classification → category, priority, confidence
  6. Worker calls PATCH /internal/problems/:id with the x-internal-api-key header
  7. Backend validates the key, updates the row, sets status=verified
  8. Backend emits problem_verified to the admin room via Socket.io
  9. Admin calls PUT /problems/:id/assign
  10. Backend sets status=assigned and inserts a project stub
  11. Backend emits problem_assigned to the assigned university's room
SHEET 07 / SECURITY MODEL

7. Security Model

  • JWT required on every route except /auth/login and /auth/register, verified by auth.middleware.
  • RBAC middleware runs after auth and checks the role claim: assign → admin only, problem creation → citizen only, proposals → university only, funding → industry only.
  • Internal API key is a static secret compared with constant-time comparison, never exposed to the frontend.
  • Rate limiting recommended on /auth/* and POST /problems to prevent abuse.
  • Input validation on every mutating route before it reaches the controller.

SHEET 10 / ERROR HANDLING

10. Error Handling Strategy

Controllers wrap logic in try/catch and forward errors to error.handler via next(err). Standard error shape:

{ "error": { "code": "VALIDATION_ERROR", "message": "Title must be at least 5 characters" } }

Status mapping: 400 validation · 401 unauthenticated · 403 unauthorized role · 404 not found · 409 invalid state transition · 500 unhandled.

Do not leak stack traces or raw DB errors in production responses — log them server-side instead.
SHEET 11 / DEPLOYMENT ARCHITECTURE

11. Deployment Architecture

This backend is a stateful, long-running server. It needs a Node.js process host, persistent DB connections, an always-on worker process, and WebSocket support — none of which static hosting provides.

SuitableNot suitable
Render, Railway, Fly.io, AWS (ECS/EC2/EB), DigitalOcean App Platform, HerokuGitHub Pages, Netlify static hosting, Vercel static export

   │  CI/CD (GitHub Actions)
   ▼
Render / Railway (API + Worker services)
   │
   ├── Neon / Supabase (Postgres)
   ├── MongoDB Atlas (Mongo)

  1. Initialize package.json; install Express, TypeScript, pg, Mongoose, ioredis, BullMQ, Cloudinary SDK, jsonwebtoken, bcrypt, Zod, express-rate-limit.
  2. Create .env; write connection modules with retry/backoff for Postgres, Mongo, Redis.
  3. Define models/schemas for User, Problem, Project, Notification.
  4. Implement auth.middleware and rbac.middleware.
  5. Build Register/Login and test with Postman.
  6. Build POST /problems; confirm DB insert + Redis enqueue.
  7. Build PATCH /internal/problems/:id; test with the internal key header.
  8. Write worker.ts as a separate process; confirm it consumes jobs and calls the internal API.
  9. Build the assign route (status update + project stub).
  10. Attach Socket.io; emit events on verify/assign/fund.
  11. Add centralized error handling and rate limiting.
  12. Set up CI/CD to Render/Railway with managed DB add-ons.
